## Verdict vocabulary (exactly one per row)

- `confirmed` — a current source (tiers 1–7) states the same claim, or the claim is directly observable now (code, DB, file). This is the corroboration gate for promotion to `verified`, so the bar is real: name the file:line or query.
- `stale` — a current source contradicts the claim, or the thing it describes no longer exists / was replaced / was overturned by a later ruling. Name the contradicting source. Say in `reason` what changed.
- `superseded_by_row` — another memory row (verified or proposed) states the same thing more accurately or more recently, OR a `decision` row resolves this `question`/`wishlist`. Put that row's slug in `superseded_by`. (Use the SELECT below to search rows by keyword.)
- `snapshot` — a measurement / count / state that was true on its event_date and is expected to drift (row counts, "N of M", a config value quoted, "awaiting X"). If you can cheaply re-measure it and it still holds → `confirmed` (say so); if it no longer holds → `stale`; only when re-measuring is not cheap use `snapshot`.
- `unverifiable` — no current source either way. Plausible claims with nothing committed to test them against land here. This is a fine answer; do not stretch.

Also fill:
- `human_sourced`: true when `verified_by`, `source`, `author`, or the text itself attributes the claim to a named human — Sam / Sam Lee / slee@, Jenni, Ashley, Jessica, Malone, "curator", any email address, "(screenshot …)", "Sam ruled", "Sam said". Give the name in `human_name`. Your verdict on such a row is ADVISORY — it will go to Sam on a sheet, never be applied by a session.
- `kind_check`: if the row's `kind` looks wrong (e.g. a `question` that is really a decision, a `fact` that is really a `milestone`), say the better kind; else null.
- `link_fixes`: dangling `related` slugs or dead file paths you noticed, as suggestions (`{"from": "...", "to": "..."}`); else [].
- `confidence`: high / medium / low — how sure you are of the VERDICT given the evidence.

Do not mark a `decision` row stale merely because the decided thing has since been built; a decision that still governs is `confirmed` by the thing that implements it. Mark it stale only if a later ruling overturned it. Do not mark a `pitfall` stale because the bug was fixed — a pitfall is a lesson; it is stale only if the lesson itself is wrong or the mechanism no longer exists at all (say which). A `milestone` is `confirmed` if the event happened (git log / lessons doc suffice for that).

## How to pull your rows

Step 1 — load the tool: `ToolSearch` with query `select:mcp__Supabase__execute_sql`.

Step 2 — the partition. Every auditor uses this same SQL so the slices are disjoint and cover all 527 proposed rows. Substitute your PART name.

```sql
with b as (
  select id, created_at,
    case
      when tags && array['memory-tab','memory','cpl-memory','briefing'] then 'memory'
      when tags && array['funding','implementation-funding','cpl-funding','allocation','budget','one-pool','ess-25-82'] then 'funding'
      when tags && array['sierra','cpl-chat','retrieval','sierra-guidance','chatbot','rag'] then 'sierra'
      when tags && array['ccr','skyview','subj4','esl','remint','m-id','identity','ccrr','cr-reference','alignment','articulation','coci','unified-courses','common-course','csr','discipline'] then 'ccr'
      when tags && array['governance','doctrine','sam-ruling','docs-corpus','documentation','decision','process','checkpoint','claude-md','handoff'] then 'governance'
      when tags && array['auth','rls','admin','navigation','security','phrase','reviewer','session','sign-in','magic-link'] then 'auth'
      when tags && array['noncredit','cip','nc','learning-partners','apprenticeship','cdcp'] then 'noncredit'
      when tags && array['custom-report','map-api','map-custom-reports','map','map-platform','disposition','student-detail','privacy','disclosure','metrics','my-college','contacts','map-users','ferpa'] then 'map-data'
      when tags && array['gr','regulation','title-5','ed-code','legislation','statute'] then 'gr'
      when tags && array['military','ace','crosswalk','partner','college-identity','eacr','exhibit','district'] then 'crosswalk'
      when tags && array['data-quality','curation','worklist','data-integrity','matching','joins','dedup'] then 'data-quality'
      else 'engineering' end as bucket
  from cpl_memory where status='proposed'),
r as (select id, bucket, row_number() over (partition by bucket order by created_at) as rn, count(*) over (partition by bucket) as bn from b),
p as (select id, case when bn > 60 then bucket||'-'||(((rn-1)*2/bn)+1)::text else bucket end as part from r)
select m.id, m.slug, m.kind, m.title, m.summary, m.detail, m.plain, m.tags, m.source, m.affects, m.related,
       m.author, m.verified_by, m.event_date, m.created_at::date as created, m.updated_at::date as updated, m.confidence
from cpl_memory m join p on p.id = m.id
where p.part = 'PART'
order by m.created_at
offset 0 limit 8;
```

Page with `offset 0/8/16/…` (8 rows per call keeps each result readable; `detail` can be 4,000 chars). Stop when a page comes back empty. Count your rows against the expected N for your part.

Keyword search for related/superseding rows (any status):
```sql

from cpl_memory where status <> 'superseded' and (title ilike '%KEYWORD%' or summary ilike '%KEYWORD%' or tags && array['TAG'])
order by event_date desc nulls last limit 15;
```
