## What we learned

1. **One store, many derived readers — de-hardcode is the whole game.** Every surface (Activities
   tab, RACI, Annual Report, Fact Sheet, Sierra, reports, Element Map) is a *consumer* that
   derives titles from Supabase via the regenerated `CPL_Data.js` snapshot. The "authoritative
   place" isn't a tab — it's the store. The work was (a) pick one editor UI and (b) delete the
   hardcoded copies that had drifted (the reports literally showed a different Activity 3 name
   than the store). Fact Sheet + Sierra are *separate* content stores — they don't carry these
   titles, so nothing to wire.

2. **Adversarial review caught a dead de-hardcode via a join-key mismatch.** `buildActivityDesc()`
   keyed the map by the short `"Activity N"` id, but the report generators looked it up with the
   *full* `projects.activity` label — so `actInfo` was always `{}` and my title override never
   ran (and the formal desc paragraphs never rendered). Three reviewers converged on it, verified
   against the committed `CPL_Data.js`. **Lesson: when you "flow" a value into a lookup, verify the
   lookup KEY matches — a de-hardcode that reads the right source but joins on the wrong key is
   silently dead.** Guarded with a test that renames `activity_kpis[].activity_name` and asserts it
   reaches the report title.

3. **Two different "links" in the workplan — only one was complete.** `projects.workplan_activity`
   (text) = the home Activity + grouping key (parsed by NUMBER, so its name-part is cosmetically
   irrelevant and can drift harmlessly). `workplan_activity_associations` (N-to-N) = the
   "Contributes to" cross-links. Everything *displayed* right (via workplan_activity) but 10
   projects had no real association row. See the reference KB note.

4. **A tabled item is more entangled than its label.** "Delete Activity 5" looked like 2 label
   rows but was 6 associations (4 stale secondary on active projects + 2 ghost primaries) + a
   tabled `5.1` (AI-Ready California) with a ladder + a RACI row + an update row + a lifecycle
   row. I surfaced the entanglement and did NOT blanket-delete until Sam confirmed 5.1 was
   disposable — then removed it across all 6 tables atomically.

5. **The generator can't run in the sandbox** (no Supabase reach, Rule 9c). Verification was:
   `py_compile`, jsdom tests for every JS surface, an adversarial-review workflow on the diff,
   and a **post-merge `daily-dashboard.yml` dispatch** as the first real end-to-end exercise
   (with a scheduled self-check to catch a generator trip).

  *smallest* associated Activity id (`activity_ids[0]`), so a cross-linked project (e.g. `2.3`

## What we learned (this batch)
1. **A reorg re-key must touch EVERY project-keyed table, or a left-behind table mis-aligns
   silently.** #872 re-keyed 3 tables and left 2. The ladder table on the old numbering produced a
   convincing-but-wrong display (off-by-one under a dissolved slot) — not a crash, so it hid for
   days. **Discover the full keyed-table set from `information_schema.columns` before AND after a
   re-key** (project_id / item_id / activity_id / id). The crosswalk from the original receipt is
   the fix — apply it to the tables that were missed.
2. **Two tables, one tree: make the entity table authoritative and the other a pure overlay.**
   The Activities tab iterated `projects`; Annual Goals iterated `workplan_goals`. Two consumers
   iterating two tables *will* drift. Path A makes `projects` the single source of the sub-activity
   tree and `workplan_goals` a by-id ladder overlay — now they can't diverge, and a new project
   auto-appears on both.
3. **A reflected-but-unbacked row must be read-only on the fields it can't persist.** The blank
   ladder rows have no `workplan_goals` row, so their year/Current cells can't be PATCHed — gate
   the editable attributes on `has_ladder` (title+description still edit `projects`). An editable
   cell that PATCHes 0 rows is a silent-revert UX trap.
4. **Trace consumers before a data/generator change (Sam's standing reminder).** A dedicated
   consumer-trace subagent confirmed RACI / Fact Sheet / all 5 report generators need no change —
   and that the re-key *corrects the reports for free* (they read `projects[*].kpi_goal_*`, ladder-
   enriched from `workplan_goals` by id). It also caught the 3 blank-row fixes (read-only gating,
   `is_percentage` guard, all-keys-present) py_compile + the existing tests would have missed.
5. **Re-homing an id-nested item means renumbering it** (there's no separate parent-pointer field;
   nesting is id-prefix based, per `methodology-tree-from-dotted-ids-stable-keys`). `4.7`→`4.5.1`
   is a "renumber to re-parent." Fine for a small item with no ladder; a laddered item would also
   need its `workplan_goals` row re-keyed.
