# SkyView search: the deferred commit — handoff

Session 236 (SkyFacet), 2026-09-06. Branch `claude/video-project-2-frames`.
Next session is running in the **cloud environment**.

## What this changes, and why

Sam, watching the dropdown misbehave on a screen recording:

> "Seems the problem is firing the routine to add the filter is the problem.
> **Why not wait on that step until the user hits enter.** That would be my
> normal expectation when choosing from multiple options."

and, a moment later:

> "**Enter should dismiss the box.**"

Before this change, ticking a row committed the pick on the spot: it added a
token, flew the map, and — the actual defect — called `openSug()`, which
**rebuilt the list from scratch**. The rebuild reset `sugShown` to one page, so a
reader who had scrolled through 120 rows watched the list collapse to 60 and
jump under their cursor mid-selection.

S233 tried to fix this by restoring `scrollTop` after the rebuild. That could not
work: the row that offset pointed at was no longer the same row, because the list
underneath had been re-cut. **The fix is to not rebuild at all.**

Now: a tick writes to a pending set and repaints that one row. Enter applies the
whole set in a single operation and closes the box. Escape abandons it.

## Design decisions Sam settled

| Question | Ruling |
|---|---|
| Tick commits immediately? | **No** — Enter commits |
| Enter dismisses the box? | **Yes** |
| Tick survives refining the term? | **Yes** — keep it, commit on Enter |
| Clearing the search box? | **Keeps ticks** — only Enter or Escape ends a session |

The last two came from Sam watching a tick disappear: he ticked "Introduction to
Welding" on `weldi`, typed one more letter, and the tick was gone — the row still
listed, still matching, no longer ticked. Refining a search is *how you hunt for
the next thing to add*, so a session now spans every term the reader types.

## ⚠️ This reverses item 6 of the SAME DAY — read before touching Enter

Item 6 (2026-09-06) was "Enter no longer hides the answer": Enter used to close
the list and fly the map on a **ranking**, dismissing the very row Sam was
hunting for. That protection is now gone, and the reversal is safe **only because
ticking no longer commits** — Enter closes on rows the reader chose by hand, so
there is nothing left to guess.

**If ticking is ever made to commit on the spot again, item 6's protection has to
come back with it, or the original bug returns.**

## ⛔ OPEN BUG — start here

**A pick is silently lost when it is ticked under one term and committed under
another.**

Reproduce (failing test, already written and pointing at it):

```bash
node tests/ccr_skyview_search_show.test.js
```

```
FAIL  (11a) ⭐ Enter applies both ticks, so the selection is now two picks  — 1 -> 2
```

Tick two rows on `welding`, refine the term to `weldi`, press Enter. Both rows
stay ticked and the footer correctly reads "2 to add" — so `pendKeys` holds both.
But only **one** token is committed.

The prime suspect is the `.filter(Boolean)` in `commitPending()`
(`prototype/ccr_atlas_v1.html`, ~line 995):

```js
var add = pendKeys.filter(function(k){ return have.indexOf(k) < 0; })
                  .map(function(k){ return pendItem[k]; })
                  .filter(Boolean);          // ⚠️ silently drops a missing item
```

`pendItem[k]` is only written in `toggleRowAt()`. `seedPending()` deliberately
resets `pendItem = {}`, so any key seeded from an already-committed token has no
item — harmless, since those keys are never in `add`. Something is nonetheless
leaving a *ticked* key without an item across a term change.

Two things to check first:

1. Whether `keyOf(it)` (which builds `pendKeys`) and `tokenFromSuggestion(s).key`
   (which builds the committed token) can disagree for the same row. If they can,
   identity is inconsistent between the pending and committed sides and the
   dedupe in `__ccrCommitSelection` will mis-fire.
2. `.filter(Boolean)` should not stay as-is regardless of the cause. It converts
   "I cannot find this pick" into "the reader did not pick it" — exactly the
   class of silent discard this whole change exists to remove. Make it loud.

**Not yet verified in a browser.** The failing case is currently only reproduced
in jsdom; confirm against the real page before and after fixing.

## ⚠️ THE DROPDOWN CODE IS TRIPLICATED — this cost real time

The same search-dropdown implementation is maintained **by hand in three files**:

| File | Role |
|---|---|
| `prototype/skyview.html` | the deployed single-file build (what Sam opens) |
| `prototype/ccr_atlas_v1.html` | the page chrome — **what the tests read** |
| `prototype/ccr_universe.js` | the map module (`__ccrCommitSelection` etc.) |

A fix applied to `skyview.html` alone changes what Sam sees and **nothing the
tests check**; a fix applied to `ccr_atlas_v1.html` alone does the reverse. This
bit twice in one session — once when the tick fix appeared to have no effect on
the suite, once when a test hook was "missing."

Every change in this area must land in all three. Worth proposing that they be
generated from one source instead.

## Test hook added

`window.__ccrPendKeys()` — returns the pending (ticked-but-not-applied) set, the
counterpart to the existing `__ccrTokenKeys()` (committed). Added to both
`skyview.html` and `ccr_atlas_v1.html`. A test that can only see the committed
side cannot distinguish "the tick did nothing" from "the tick is waiting for
Enter."

## Also noted, not fixed

- **Footer overlaps the last row** at narrow widths. `.sug li.sug-more` is
  `position:sticky; bottom:0`, and when rows wrap to two lines the last one runs
  under it. Cosmetic before, but the footer now carries the primary action.
- `.claude/launch.json` added (untracked) to serve the prototype at :8777 for
  browser verification. Serves the repo root via `python -m http.server`.
