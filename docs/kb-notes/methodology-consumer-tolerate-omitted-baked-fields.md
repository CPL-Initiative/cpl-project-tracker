# Methodology — A consumer must guard fields the baked payload omits but the fallback fills

> **One-sentence summary** — when a tab renders from EITHER a lean baked payload
> OR a runtime-fetch fallback, any field the baked path omits (`null`) but the
> fallback path fills (an array/object) is a latent crash: guard it with `|| []`
> at the consumer, because one thrown render aborts the *whole* tab.

## Context

Several dashboard tabs (CER, CCR, …) prefer a pre-joined **baked** payload
(`*_data.js`, generated by `excel_to_dashboard.py`) and fall back to a **runtime
fetch** of `kb/*.json` when the baked file is absent. To keep the baked payload
lean, the producer deliberately omits some fields — but the *fallback* builder
still constructs them. The two paths therefore hand the renderer **different row
shapes**, and code written against the fallback shape silently assumes a field
exists.

## The claim

A field that is an array on the fallback path but `null`/absent on the baked path
is a render-aborting bug waiting for the first row that reaches it. In the CER
(Session 32, items 2 & 7), `passesFilter` did:

```js
|| row.raw_variants.some(v => v.raw_title.toLowerCase().indexOf(q) >= 0)
```

`raw_variants` was built by the fallback `buildRows()` but baked as `null`. The
`||` short-circuits on rows whose title/issuer match the search, so it *looked*
fine — until the first **non**-matching row, where `null.some` threw a
`TypeError`. Because the throw happened inside `state.rows.filter(...)` in
`render()`, it aborted the **entire** render — freezing not just search but every
other control too (the expand wedges "stopped working"). One guard fixed both
symptoms:

```js
|| (row.raw_variants || []).some(...)
```

**Two complementary moves, do both:**
1. **Guard at the consumer** (`|| []` / `|| {}`) for every field that differs
   across the two shapes — this is the safety net regardless of payload state.
2. **Bake the field properly** when the feature actually needs it (Session 32 also
   baked `raw_variants` + per-local-course `u` units so items 4 & 6 had real data)
   — but the guard stays, because the baked file can lag (e.g. before the first
   cron, or local dev).

## How we got here

The user reported "search doesn't fire" and "expand stopped working after the
first two exhibits" as two separate bugs. Both were the single `null.some` throw:
typing in search set `state.search`, every subsequent `render()` threw on the
first non-matching baked row, so the tab froze wholesale. Verified by a jsdom test
that types in the search box and clicks expand wedges with search active (20/20).

## When this applies (and when it doesn't)

- **Applies** to any consumer with a baked-payload-OR-runtime-fetch dual path
  (the standard shape in this repo). Audit `adaptBakedRow()` (or equivalent)
  against the fallback `buildRows()` for fields set to `null` on one side and an
  array/object on the other; guard every consumer read of them.
- **Doesn't apply** when a single code path produces the rows (no shape
  divergence) — though `|| []` on `.some`/`.forEach`/`.map` of a possibly-absent
  field is cheap insurance anyway.
- **Test signal:** a render that throws inside `.filter`/`.map`/`.forEach` aborts
  the whole tab, so the failure mode is "the entire surface is dead," not "one row
  is wrong." A jsdom test that exercises the control with a *non-matching* row
  present catches it; one with only matching rows won't.
