# CCR curation sync & live-merge durability

The recurring confusion (Sam hit it Session 69 after a 12→1 merge): *"do I lose my
merges if I don't wait for the cron?"* **No.** A merge is durable the instant you
click. Here's the precise model — what's instant, what waits, and why per-click
regen is the wrong tool.

## Three layers, three speeds

1. **Instant (server-side, durable):** clicking Merge writes the `merge_into` rows to
   **Supabase `kb_curation`**. Saved immediately; survives anything.
2. **Instant (in-browser, live):** `doConsolidate()` marks the absorbed members
   `_mergedAway` and calls `render()`; `passes()` excludes `_mergedAway` rows, so they
   **drop out of the CCR list immediately** and the target shows `⛓ N merged`. On the
   **next page load**, `replayLiveMerges()` re-reads `kb_curation` and re-applies the
   merges, so they **persist across reloads** with zero cron involvement.
3. **Deferred (the daily cron OR a dispatch):** `kb/_apply_curation.py` folds
   `kb_curation` into `kb/coci_curation.json`, then `export_unified_courses()`
   regenerates `unified_courses_data.js`. This is the **only** step that recomputes the
   merge target's **aggregate columns** (Members / Units / TOP / clean identity) — those
   need the Python generator over the 24 MB COCI source, which the browser doesn't hold.

So: the **fold** (absorbed rows gone, `⛓ N` badge) is live and durable; the target's
**recomputed aggregates** are what "fully materialize on the next sync."

## Why per-click regen is infeasible (and unnecessary)

`export_unified_courses()` re-reads 141k COCI rows and rebuilds ~16k catalog rows +
~100 MB of lazy artifacts + the Excel export — a multi-minute job on a CI runner, not in
the browser. Firing it per click would be minutes each and would **race itself** on
successive merges. It's also unnecessary: layers 1–2 already make the merge real and
visible. **The CCR's own data (`unified_courses_data.js`) is regenerated by the SAME
`daily-dashboard.yml` as the dashboard** — so "regen the CCR" = a single **`Sync now ↗`**
dispatch of that workflow, not a per-click routine.

## The right cadence

**Merge freely → publish once.** Curate a whole session (live fold tracks each merge),
then either let the overnight cron publish or trigger **one** `daily-dashboard.yml`
dispatch (`mcp__github__actions_run_trigger`, or the badge's `Sync now ↗` link) to
materialize the batch in ~10 min.

## The visibility gap (separate from durability)

Durability is solved; **tracking** is the open UX item. The `⟳ N edits awaiting daily
sync` badge (`pendingSyncCount()` counts `liveMergePending` + discipline/description
deltas) shows only a **count**. A **Pending-merges review panel** (click the badge → the
session's merges as target ← absorbed members, each with an undo) closes that — all
client-side off `kb_curation`, no pipeline change. That's the build, not a regen routine.
