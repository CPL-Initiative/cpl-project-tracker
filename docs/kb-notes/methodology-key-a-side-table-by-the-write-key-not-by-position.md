# Key a side table by the write key, never by list position

> **One-sentence summary** — a derived table aligned to a list by index is
> silently wrong the moment any consumer drops one element of that list; key it
> by the same key the write uses and a drop becomes harmless.

## Context

SkyView shows a college course's catalog description when a curator clicks its
number. The descriptions ship as one shard per subject area, fetched on demand,
and the first shape was `{identity: [text, text, …]}` — one text per member
course, **in the order of the members list**. The members payload the map draws
from is built from the same list but **drops a member whose control number is
missing** (two are), because the control number is the write key
(`CN:<control number>`) and a course without one cannot be re-homed. Every
description after a dropped member on that identity then belonged to the wrong
course. Nothing looked wrong: a description rendered under a code, and the
inspector cannot tell a right paragraph from a plausible one.

## The claim

**When two artifacts are cut from one list and one of them may filter it, align
them by a key, not by position.** The right key is the one the eventual write
uses, because that is the key every layer already has to carry: the shard became
`{ "<control number digits>": [description, title, units] }`, the member record
stayed `[control number, code, college]`, and the lookup is a dictionary read.

Three properties fall out, and each was a separate defect waiting under the
positional shape:

1. **A drop is harmless.** The keyless member simply has no shard entry; every
   other course keeps its own text.
2. **A rebuild is harmless.** The layout is regenerated by hand while the shards
   follow the daily artifacts; keyed by control number, a shard built on Tuesday
   still serves a layout committed on Monday.
3. **The side table can carry more.** Once it is a keyed record, adding the
   course title and units (which the drag list deliberately left out of the
   members payload to save 3.1 MB) costs nothing structural — they ride in the
   shard and appear when it loads.

## How we got here

Re-reading `write_desc_shards()` beside `write_members()` while wiring the new
inspector: one loop indexed `texts[k]` for `members[k]`, the other loop
`continue`d past a member with no key. The two were written by the same session
and had never disagreed because no identity with a keyless member had been
opened with descriptions loaded. The guard is now in
`tests/ccr_universe_orbits_test.py`: a synthetic identity with a keyless second
member must leave the third member's description on the third member.

## How to apply

- When you add a side table (descriptions, titles, receipts, per-row notes) to
  an existing list, ask what the consumer of the list is allowed to drop or
  reorder. If the answer is anything, key the table.
- Prefer the write key — the identifier the write path already validates —
  over a synthetic index. It is the one identifier guaranteed to exist wherever
  the write can happen.
- Test the drop, not the happy path: a fixture with one filtered element and an
  assertion on the element AFTER it is the whole test.
