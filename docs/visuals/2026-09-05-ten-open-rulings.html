An admin view that fires a re-mint

queue, do not fire
What you asked
“Should I have an admin view that allows me to fire a remint?”
Why I am pushing back
Rule 7 makes the re-mint playbook mandatory — dry-run, alias map, kb/promotions.json re-key, atomic land inside one cron window. A button that fires a re-mint from the interface steps around all four. And a re-mint is not reversible from its receipt the way an insert cohort is: Rule 10 (a2) can be satisfied by an insert’s reviewer_email, but there is no equivalent undo for a re-key that has already rippled through the alias chain.
Proposed
Build the queue, not the trigger: each candidate with its reason and evidence, you approve or reject, and the approved set lands through the existing playbook on the next cron window. Same control for you, without the bypass. It is also a new write surface, so it routes through Governance and the privacy ADRs before it ships (Rule 10 a3).

8

Where the alias-chain rule should live

build
The failure it has to prevent
Comparing an id read from any stored file against the live identity set without resolving it first. It returns a confident, plausible, wrong answer — I did exactly this tonight and reported 44% and 36% where the truth is 27% and 22%.
Proposed — four layers, strongest first
(a) One shared kb/alias_chain.py holding the single map list and a resolve(); both existing callers import it, so the lockstep invariant cannot be violated because there is only one list. (b) A CI guard that fails if any file declares its own ALIAS_MAPS — the layer that fires without being read. (c) One line of PUSH in CLAUDE.md: an id read from a stored file is resolved through the chain before it is compared to the live set. Rule 7 files this as PULL, triggered by “you know you are re-minting” — and I was not re-minting, which is precisely why I walked into it. (d) A cpl_memory row, understood as the weakest layer rather than the answer. (c) costs context in three repos on every session, so it is the one worth vetoing if you think three layers are enough.

11

A skill or harness for memory adherence

build — layer two
What you asked
“Maybe there’s a skill or harness we could write to invoke when unsure about memory adherence.”
It already exists, and it already knows its own weakness
kb/doctrine.py — “what has this repo already decided about the files I am about to touch?” — was built on 2026-08-21 after Session 178 shipped four defects that were each covered by a rule already committed here. Its clever part is that --changed reads the diff, so it needs no knowledge of which note matters. Its docstring already says the rest: “this still has to be INVOKED, which is the same weakness as any rule that lives in prose… The mechanism that needs no invocation is a test.”
Why it would not have caught me tonight
It reads the diff. My error was in analysis — I ran a throwaway script, read four files and edited none, so the diff was empty and doctrine would have had nothing to say. It covers files you write, not files you read. That is the gap, stated precisely.
Proposed — and the reason it is layer two, not one
Write the skill: a skill fires on its description matching the task, not on anyone remembering it, so one described around resolving course or M-ID identifiers from a stored file against the live identity set plausibly matches what I was doing tonight. That is a real automatic trigger and strictly better than a memory row needing an explicit query. Alongside it, give doctrine.py a read-side mode so files consulted count like files changed. But the ceiling is honest: anything requiring a decision to invoke will not fire in the case that matters, because the failure mode is confidence, not doubt. I was not unsure tonight. That is why item 8(a) — one shared module, so the wrong call is impossible to write — beats every layer above it. The best rule is the one you cannot not follow.
